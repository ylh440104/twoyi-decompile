## `hal/` is one fake per file, and they all use LocalSocket

The `hal/` package is 50+ files and was the largest unexamined block. Its
imports give the whole map without reading every body: every implementation
imports `android.net.LocalSocket`, and each pairs it with exactly one Android
service type.

| file | faked Android service |
| --- | --- |
| `a1.java` | `Sensor` / `SensorManager` |
| `c1.java` | `Vibrator` / `VibrationEffect` |
| `b1.java`, `d1.java`, `e1.java` | `ConnectivityManager`, `Network`, `NetworkCapabilities`, `LinkProperties`, `LinkAddress` |
| `g0.java` | `CameraManager` |
| `r0.java` | `LocationManager` (GPS) |
| `a0.java` | `Context`, `LocalSocket`, `LocalSocketAddress` |
| `b0.java` | `Context`, `IntentFilter` |
| `d0.java` | `SystemClock` |
| `f0.java`, `j0.java` | `LocalSocket` only |
| `h0.java` | `ParcelFileDescriptor` |
| `KernelSuHal.java` | `LocalSocket` + `ParcelFileDescriptor` — su emulation |
| `TwoyiResolverHal.java` | `LocalSocket` — DNS |

So the architecture is uniform: **each `hal/*.java` is a userspace stand-in for
one Android hardware service, driven by the host over a `LocalSocket`, and
publishing the result through the real framework interface.** `r0.java` is the
clearest example — it imports `android.location.Location` and
`LocationManager` alongside `LocalSocket`, so it feeds real `Location` objects
into the host's `LocationManager` from socket data.

## `configureEndpoints` / the socket paths: no concatenation in C

`SOCKET-CHANNELS.md` left open how the socket path is assembled. Reading
`FUN_00328660` and `FUN_00329448` settles it — and the answer is that **the
path is never concatenated in native code**.

Both are the same shape:

```c
void FUN_00328660(void) {                    /* and FUN_00329448 identically */
    FUN_009c0920(&DAT_00a6c518);             /* mutex lock */
    puVar5 = FUN_009e0490(0x440);            /* operator new(1088) */
    lVar6  = FUN_0031a400();                 /* shared config object */
    FUN_003387f0(local_70,
                 *(long *)(lVar6 + 0x28), *(long *)(lVar6 + 0x20));   /* (ptr, len) */
    DAT_00a6c510 = puVar5;
    FUN_009c0a64(&DAT_00a6c518);             /* unlock */
}
```

- `0x440` = 1088-byte channel singleton, one per socket role.
- `FUN_0031a400()` returns the shared config; the two functions read
  **different offset pairs** — `(0x28, 0x20)` for one, `(0x40, 0x38)` for the
  other. Two `std::string`s, eight bytes apart each.
- `FUN_003387f0(ulong *dst, void *src, ulong len)` is `std::string::assign`.
  Proof: its first branch is `if (param_3 < 0x17)` — 23 — which is exactly
  libc++'s small-string-optimisation threshold (SSO capacity 22). That is not
  a path-length check, it is the inline-vs-heap copy decision.

The only place a length is computed is `bind()`:

```c
iVar11 = bind(iVar9, local_88, (int)sVar14 + 3);
```

`strlen(path) + 3` = `offsetof(sockaddr_un, sun_path)` (2) + length + NUL. That
is the standard way to size a `sockaddr_un`, not concatenation.

Conclusion: **`Renderer.configureEndpoints(String x6)` stores six endpoint
strings in the config object; the native channel constructors pick two of them
by offset and copy them into `sockaddr_un` buffers.** The strings originate in
Java, which is consistent with `%s` in the render banner
`G5 ready socket=%s ...` and with `Renderer socket directory is not configured`
being a Java-side condition.
